# Files

Per-module responsibility reference for note-color, one row per file, split out of `CLAUDE.md` (map #145's package-layout note in that file explains the package grouping these files sit under) so the project's always-loaded instructions stay small — this table is looked up on demand rather than loaded into every session, the same convention `docs/DECISIONS.md` already uses for full design rationale.

| File | Responsibility |
|---|---|
| `config.py` | All tunable constants (sample rate, buffer sizes, thresholds, color/animation/chord-mode params). Check here first. |
| `audio_capture.py` | `AudioCapture` — `sounddevice.InputStream` callback → bounded drop-oldest queue. `resolve_loopback_device()` finds the system-output monitor for `--source loopback`. |
| `pitch_detect.py` | `compute_spectrum()` — shared FFT reused by YIN, chroma, and (via its own Hann-windowed variant) multipitch. `detect_pitch()` — hand-rolled YIN (pure NumPy, FFT autocorrelation + parabolic interpolation) over a precomputed spectrum. |
| `note_smoother.py` | `NoteSmoother` — silence/confidence gate, median filter, debounce, onset detection (monophonic path): note-change, an RMS jump, or (issue #55) `onset_detect.spectral_flux()` clearing `ONSET_FLUX_THRESHOLD` against the hop-over-hop spectrum. `onset_backdate_hops` (issue #70) — 0 normally, `DEBOUNCE_HOPS - 1` on the exact hop a genuine note-change promotion fires (never on an RMS-jump/flux re-attack of an already-current note) — the fixed, known lock-in delay `main.py` backdates `DurationTracker`'s `onset_hop` by so a note's measured duration isn't systematically shortened by the smoother's own debounce buildup. |
| `chroma.py` | `fold()`/`fold_bass()` — 12-bin chroma vector via a precomputed Gaussian log-frequency weighting matrix summing 1st–4th harmonics per pitch class; `fold_bass()` restricts to <~250Hz for bass/inversion detection. |
| `chord_templates.py` | ~360-template dictionary (30 qualities × 12 roots) + `match()` — cosine-similarity chord recognition, bass-chroma-gated slash/inversion naming and rotational-tie-breaking. |
| `multipitch.py` | `detect()` — spectral peak-picking (own Hann-windowed FFT, not the shared one — see Key design decisions) + harmonic-consistency pruning, up to 6 simultaneous notes with confidence, candidate peaks bounded to `min_freq_hz`/`max_freq_hz` (issue #74, default `DEFAULT_MIN_FREQ_HZ`/`DEFAULT_MAX_FREQ_HZ` matching `config.FMIN`/`FMAX` — real callers pass those config values explicitly) so out-of-range broadband/percussive noise content can't be peak-picked into a phantom note. `select_window()` (issue #63) picks which ring buffer a hop's `detect()` call should analyze — the app's normal live `config.WINDOW_SIZE` window, or a longer `config.MULTIPITCH_LOW_WINDOW_SIZE` one the caller (`main.py`/`batch_transcribe.py`) also maintains, gated on `chroma.fold_bass()` showing real low-frequency content — see Key design decisions for why the short window alone garbles close-together bass notes. |
| `synth_corpus.py` + `evaluate.py` | (map #123, ticket #144) A **synthetic jazz corpus with ground truth correct by construction**, and the scoring harness for it. Generates drums / walking bass / comped chords / melody from ii-V-I, minor ii-V-i, blues and rhythm-changes charts, deterministic from a seed, with dialable tempo, meter, density, swing and instrumentation; pitched parts render through `playback.render_offline()` and drums reuse `scripts/acoustic_pipeline_test.py`'s existing kick/snare/hi-hat models, so **no new dependency and nothing newly synthesized that this project did not already have**. `evaluate.py` implements #132's metric triple — **F0.5** (β a stated editorial choice, not a measurement), **ghost and miss rates per bar** kept separate, and **editor operations to correct**, counted in `score_editor_display.py`'s own mutation set so a right-pitch/wrong-duration note is priced as the single keypress it is. **This is a regression and diagnostic harness, never the accuracy claim**: it is what Slakh2100 already is, and #124's standing caveat is that good Slakh numbers do not transfer to real recordings (~60% synthetic vs **37.87%** real). Numbers here run *higher* still, since Slakh at least uses professional sample libraries. Two traps recorded rather than solved: a generator's own errors are invisible (if the swing is actually straight, a converter transcribing straight scores 100% forever), and chord ground truth is circular. |
| `docs/eval/corpora.toml` + `scripts/check_corpora.py` | (map #123, ticket #133, protocol #132) The committed record of what evaluation material is *expected* to exist locally, and a checker that reports what is actually staged — **downloads nothing**, since the public corpora are large and separately licensed and the owner's own set is commercial music that cannot be fetched at all. Every URL was checked live when written. The material never enters the repo (numbers derived from it are facts and are publishable; the audio is not). `check_corpora.py` reports the owner's own pairs by **usability rather than presence** — a song sitting next to a PDF looks staged and cannot be scored, since #132's metrics compare notation to notation or notes to notes and neither reads an image, which is the trap worth catching early because bought sheet music is almost always PDF. |
| `convert.py` | (map #123, ticket #129) The converter's **pipeline driver** — owns the *order* of the passes and nothing about how any of them work, since every stage is reached through `transcribe_backends.py`'s Protocols. `convert(audio, sample_rate, separator=, note_transcriber=, beat_tracker=, chord_estimator=, want_notes=, want_chords=)` → a `ConversionResult` (`parts`, `chords`, `beats`, `beats_per_bar`, `duration_seconds`) — deliberately **not** a music21 object or a file path, since writing is #131's separate concern and #132's harness scores this shape without a disk round trip. **Asserts nothing about whether the multi-pass shape helps**: #129's H1/H2/H3 are hypotheses, and the stages are ordered so each can be switched off and measured — running with no `separator` is not a fallback but *H1's control arm*, the "without separation" half of the A/B #126 found nobody has ever run. **Refuses rather than degrades**: asking for notes with no transcriber raises `ConversionUnavailable` carrying `[convert]`'s install line, the one place that rule can actually be enforced — while chords quietly default to `TemplateChordEstimator`, which is *not* the same thing, since that tier substitutes nothing worse (it is the only chord model until an extra brings BTC). **No notated drum part** (#130): the drum stem is routed to `BeatTracker.track(drum_stem=)` as the timing oracle and skipped as a part. Chords are estimated on the **drums-removed sum of stems**, not per stem — a chord is a property of the whole harmony. `infer_beats_per_bar()` is #130's meter gate: modal beats-between-downbeats over `METER_CANDIDATES` (2,3,4,6), requiring `METER_MIN_BARS` bars and `METER_MIN_AGREEMENT` (0.6) agreement, returning `(numerator, committed)` — an uncommitted guess still writes 4/4 but surfaces as `beats_per_bar=None` so the manifest can record that it was not inferred, which is "correctable guess" made concrete. |
| `transcribe_backends.py` | (map #123, ticket #129) The **offline converter's seam** — what `detection_backends.py` is to the live path, for the offline one, and for the same reason: #129 settled that every model in the stack is a *default to be replaced by whichever #132 measures as better*, and that three of the pipeline's structural questions (does separation help note accuracy, does a locked beat grid beat independent snapping, does ensembling pay) are **hypotheses**, not architecture — none of which is possible if swapping a model means surgery through a monolithic `convert()`. Four `Protocol`s, one per pipeline stage: `Separator.separate()` (Demucs' own stem vocabulary, since every routing rule is written in those terms), `NoteTranscriber.transcribe()`, `BeatTracker.track(..., drum_stem=)` (#130's timing oracle, offered as an extra channel; a tracker that can't use it ignores it rather than failing) and `ChordEstimator.estimate(..., beats=)` (#141's Real Book half). Value types `TranscribedNote`, `BeatGrid`, `ChordSpan`. **Note events are seconds-and-MIDI, not hops-and-pitch-classes** — the neural models emit absolute times, `batch_transcribe.NoteEvent`'s `onset_hop`/`duration_hops` are an artifact of the DSP block clock, and every metric #132 adopts (`mir_eval`, `musicdiff`, MV2H) is defined over seconds; backends convert at the edge. `BeatGrid` carries **no tempo field** — #130/#131 store tempo as a *curve read back out of* these times, never a scalar imposed on them — and `beats_per_bar()` is #130's meter-numerator inference in its simplest form (the mode of beats-between-downbeats, the route chosen over madmom's DBN because madmom needs a git pin on 3.14); the caller applies the confidence gate and the {2,3,4,6} candidate set, and the **denominator is never inferred anywhere** — it is a convention. `ConversionUnavailable` mirrors `synth_engine.SynthUnavailable` (#111), carrying the install line, because #129 settled the converter **refuses rather than degrades**. `DspNoteTranscriber` is the one concrete backend so far and is deliberately **not** a fallback — it exists as #132's *baseline arm*, so "better than what this project already had" is a measured comparison rather than an assumption. `DemucsSeparator` is the `Separator` — `htdemucs`, 4 stems, measured by #126 at **~2.1× real time** (a 4-minute song in ~8.3 min) and **the pipeline's dominant cost**, ~15× everything else put together, which is why any speed dial (#134) varies *this* and why #126 recommends `overlap` rather than a lighter model as the fast end (`mdx_extra_q` measured slowest *and* hungriest despite the smallest weight file). Its weights are the one non-permissive thing in the stack, so `model_terms_accepted()` implements #139 category 2 literally: the terms are **printed verbatim** — code MIT, weights "provided only for scientific purposes", source repos stating no licence at all — and nothing downloads until the user says yes, pre-answerable via `[preferences].accept_model_terms` so a batch run isn't walled, and **declining rather than hanging** on a non-interactive stream. `prepare_separator_input()`/`stems_from_estimates()` are the pure array halves (mono→duplicated stereo at 44.1 kHz in, channel-averaged mono back at the caller's rate out), split out so they are unit-tested without torch installed — a fake torch would mostly test the fake. `BasicPitchModel` runs the **vendored** `vendor/basic_pitch/nmp.onnx` (225 KB, Apache-2.0 code *and* weights, committed under #139's 1 MB ceiling because #125 found `pip install basic-pitch` will not install on Python 3.14 — provenance, SHA-256 and the model's real I/O signature are in `vendor/basic_pitch/README.md`, with its `LICENSE`/`NOTICE` vendored beside it as Apache-2.0 §4 requires) and returns raw **`Posteriorgrams`** (`note`/`onset` 88-bin, `contour` 264-bin, on an 86 fps grid anchored at A0). Deliberately **separate from note decoding**: #143 found this model exposes exactly what frame-level ensembling and per-note confidence need, where a seq2seq model structurally cannot, and a backend that only ever returned decoded notes would throw that away — which is what basic-pitch's own `predict()` does. Windowing (43,844-sample windows, 30-frame overlap half-trimmed each end, half an overlap of leading silence so onsets don't land early) and unwrapping (trimmed to the *original* audio length, so the final window's zero padding isn't read as real frames) are implemented here against the model's actual signature rather than a description of it. Verified by running it: a synthesized A4 peaks at MIDI 69, a C-E-G triad's top three bins are exactly 60/64/67. `decode_notes()` turns those into `TranscribedNote`s — a **faithful port of basic-pitch's own `output_to_notes_polyphonic`** (Apache-2.0), not a simpler thresholder, so a number measured here is comparable with the 0.709 MAESTRO F1 #125 quotes and so a hand-rolled decoder's errors can't later be mistaken for the model's. Onset peaks → forward energy walk (tolerating `BASIC_PITCH_ENERGY_TOLERANCE` frames of dropout, consuming neighbouring pitch bins so one note can't spawn three) → the *melodia trick* second pass growing notes outward from leftover energy, which recovers notes whose onset the model missed. Local maxima are four lines of NumPy rather than `scipy.signal.argrelmax`, since SciPy is behind `[synth]` and pulling it into `[convert]` for that would be a real dependency for no reason (cross-checked against scipy itself in the tests). The per-note mean frame activation becomes **`confidence`** — #143 found basic-pitch computes exactly this and discards it into MIDI velocity, making it free, and measured within ~1 AUROC point of MC-Dropout at 50 passes; **measured here on a real C–F–G–C progression, every correct note scored ≥0.56 and every harmonic ghost ≤0.48**, so a 0.5 cut separates them. `BasicPitchTranscriber` is the `NoteTranscriber` binding the two, exposing `posteriorgrams()` alongside `transcribe()` so #143's frame-level option stays reachable. **Measured cost on this 2-core machine: ~32–38× real time** (a 4-minute song in ~7s), the CPU figure #125 found nobody publishes — negligible beside separation's 2.1×, which dominates the budget by ~15×. `_resample()` is band-limited (soxr when present, else an FFT method) and deliberately **not** linear interpolation, which was the first implementation and folded a 15 kHz tone down to 7 kHz at full magnitude when downsampling 44.1 kHz — invisible to a pure-low-sine test, ruinous on real music. `BeatThisTracker` wraps **Beat This!** (MIT code *and* weights, CPU, ~0.89 beat / ~0.78 downbeat F1 on pop-rock) with `dbn=False` — the DBN post-processor is madmom, declined by #130 for needing a git pin on 3.14, and Beat This!'s own case against it is that its 55–215 BPM and constant-meter priors break on real material. It accepts `drum_stem` and **ignores it**, which qualifies #130: reading `beat_this` 1.1.0's wheel shows `Audio2Beats.__call__(signal, sr)` takes exactly one signal and `signal2spect()` *downmixes* a 2-D input rather than accepting stems, so #127's measured drum-stem gain (0.699 → 0.775) — which came from the multi-channel **Beat Transformer** — does not transfer, and the timing-oracle role is currently unrealised. Boosting drums into the mono mix would be an unmeasured heuristic and is left to #132's harness as an experiment. Audio is passed through at its own rate since Beat This! resamples internally. `TemplateChordEstimator` is the second: chord spans from this repo's own `chroma.fold()` + `chord_templates.match()`, **no new dependency and no download** — #142's *no-extra tier* for #141's Real Book output, sitting below the neural `BTC-ISMIR19` (81.59% MajMin on 485 real pop/rock songs, MIT code with weights committed in an MIT repo), whose two obvious alternatives are both #139 licence traps (Chordino is GPL-2.0; `autochord` is Apache-2.0 *running on* that GPL plugin). Expect meaningfully less than BTC — the field's MajMin ceiling is 75–80% and plain chroma+templates is explicitly "a weaker baseline than NNLS-chroma/Chordino". Segmentation is **beat-synchronous when a `BeatGrid` is given** (one span per beat — chords change on beats, and averaging chroma across a beat is both steadier and cheaper than a fixed window straddling two), falling back to fixed windows otherwise and always covering the tail past the last detected beat; adjacent same-name spans are **merged** (four beats of C become one span, which is what `<harmony>` and a human reader want) *before* any `min_span_seconds` filter, and a segment nothing matches stays **blank rather than inheriting the previous chord** — `chord_templates.match()`'s own posture carried through. Every backend imports its heavy dependency **lazily inside the method** (`synth_engine._signal()`'s convention). |
| `detection_backends.py` | The pluggable seam between `analysis_loop()` and the two detection functions above (per `docs/research/architecture-modernization-plan.md` §3.1): `MonoPitchBackend`/`PolyphonicBackend` `typing.Protocol`s mirroring `pitch_detect.detect_pitch()`'s `(freq_hz \| None, confidence)` and `multipitch.detect()`'s `list[NoteCandidate]` return shapes exactly — nothing algorithm-specific in the Protocol itself, since `NoteSmoother`/`ChordSmoother`/`DurationTracker` already only depend on those shapes, not on how they were produced. `YinBackend`/`SpectralPeakBackend` wrap today's two functions as adapter classes, capturing all algorithm-specific config (fmin/fmax/threshold/subharmonic params, max_notes/min_mag_ratio/harmonic_tolerance_cents/etc.) once at `__init__` time instead of threading it through every call — the part that actually buys pluggability, since it moves "which config constants this algorithm needs" out of `analysis_loop()`'s body. `default_pitch_backend()`/`default_poly_backend()` build the two default backends from `config.*` exactly as `analysis_loop()` called `detect_pitch()`/`multipitch.detect()` directly before this seam existed — see Key design decisions for why `multipitch.select_window()`'s bass-gated window logic deliberately stays outside this Protocol. |
| `chord_smoother.py` | `ChordSmoother` — mirrors `NoteSmoother`'s shape for chord mode: chroma rolling-average + chord-name debounce, plus asymmetric attack/release hysteresis per note-stack slot. |
| `onset_detect.py` | (issue #55) `spectral_flux()`/`chroma_flux()` — pure, `None`-safe half-wave-rectified positive-magnitude-difference novelty measures between two consecutive `pitch_detect.compute_spectrum()`/`chroma.fold()` frames. `spectral_flux()` feeds `note_smoother.py`'s onset gate; `chroma_flux()` feeds `tempo_tracker.py`. |
| `duration_tracker.py` | (issue #55) `DurationTracker` — mirrors `ChordSmoother.note_states`' dict-of-state shape, but for *measuring* how long a note sounded rather than debouncing its display. `.update()` (live, causal, keyed by `(pitch_class, octave)`, `is_onset`-aware re-attack preemption) and `.finalize_noncausal()` (batch, centered-smoothed envelope, static method) share one off-threshold definition (`DURATION_DECAY_RATIO`). `duration_class_for_beats()`/`DEFAULT_DURATION_CLASS` — nearest-standard-note-value snapping (incl. dotted), used by both live and batch. `_TUPLET_DURATION_CLASSES`/`TUPLET_DURATION_CLASSES`/`DURATION_CLASS_ORDER_WITH_TUPLETS` (map #123, issue #130) — triplet note values (each 2/3 of its plain counterpart), in a **separate table, off by default**: `duration_class_for_beats(beats, allow_tuplets=True)` is the opt-in the offline converter passes and nothing on the live path does, so `DURATION_CLASS_ORDER` (which the live path snaps against, and which the score editor's `,`/`.` cycling walks) is unchanged byte-for-byte — adding them to `_DURATION_CLASSES` would silently make a note held slightly under a quarter start reading as a triplet-half. Needed because a converter that cannot write a triplet misnotates compound meter outright (6/8 is on map #123's own candidate-meter list); a triplet eighth currently snaps to a *dotted sixteenth*. Swing is deliberately **not** a reason — Real Book convention notates swung eighths as straight eighths under a "Swing" direction. `BEATS_BY_DURATION_CLASS` covers the tuplet names too, since once a `duration_class` exists every consumer has to convert it back. Writable to MusicXML as of the follow-up step: `score_writer.QUARTER_LENGTHS` carries the four triplet values as exact `Fraction`s (not floats — music21 normalises a quarterLength through `opFrac` and **builds the matching `duration.Tuplet` itself** from an exact third, which is what makes MusicXML emit `<time-modification>`), and `OFFSET_QUANTIZE_DIVISORS` is `(8, 12)` rather than `(8,)` in both writers — a triplet-eighth onset falls at 1/3 of a quarter and a 32nd-only grid would shift it to 3/8. `score_writer.write_score()` still deliberately does *not* opt in: that path derives beats from a single `result.bpm` scalar, exactly the input a triplet is indistinguishable from timing jitter against. `require_onset_for_new_note` (constructor, issue #70) — mono's tracker sets this `True` so a key with no existing state only opens one when `is_onset` is genuinely `True` for it, since `NoteSmoother` otherwise echoes a just-finalized note's key with `is_onset=False` for a couple more hops (its own silence grace period) that would otherwise misread as a spurious new note; chord mode keeps the default `False` since it has no reliable per-note onset signal at all and relies on appear/absence alone. `.update()`'s `onset_backdate` parameter (issue #70) backdates a freshly-opened state's `onset_hop`, fed from `NoteSmoother.onset_backdate_hops` for mono. |
| `tempo_tracker.py` | (issue #55) `TempoTracker` — live-only causal BPM estimation via FFT autocorrelation over a rolling `chroma_flux()` novelty-history window (same autocorrelation approach `pitch_detect.py`'s YIN already uses, applied to novelty instead of raw audio); re-estimates every `TEMPO_UPDATE_INTERVAL_HOPS` hops, not every hop. `_estimate()`'s best-lag candidate (issue #70) is gated on a confidence ratio (autocorrelation peak over zero-lag energy, `config.TEMPO_MIN_CONFIDENCE`) — below it, the estimate holds at its last value rather than re-locking onto what's essentially noise once the rolling window's content stops being periodic (e.g. a stretch of isolated, irregularly-spaced notes with no consistent beat). Batch tempo uses `librosa.beat.beat_track()` directly instead (`batch_transcribe.py`) — this module is never imported there. |
| `batch_transcribe.py` | (issue #55) The only module permitted to import `librosa` for *offline* transcription. `load_audio()` + `transcribe()` — runs the same per-hop pipeline `analysis_loop()` drives live (mono via `NoteSmoother`, polyphonic via `multipitch.detect()`+`ChordSmoother`), accumulates full-recording-length per-`(pitch_class, octave)` magnitude/onset arrays, then calls `DurationTracker.finalize_noncausal()` per key and `librosa.beat.beat_track()` for tempo. Returns a `TranscriptionResult` (`notes` polyphonic, `mono_notes` monophonic, `bpm`, `hop_seconds`) that `main.run_batch_transcribe()` turns into `TabDisplay` columns. |
| `score_writer.py` | (issue #65, batch-only v1) One of two modules permitted to import `music21` (the other is `score_editor_state.py`, issue #98's second permitted importer, added by the same precedent `rhythm_reanalysis.py` set for `librosa` in issue #77 — see Key design decisions) — mirrors `batch_transcribe.py`'s sole-`librosa`-importer isolation convention, for the same reason (real, one-time import cost with no business on the live/Pi-constrained path). `write_score(result, path, time_signature=...)` writes a `batch_transcribe.TranscriptionResult` to a two-staff-grand-staff MusicXML file: one `<chord/>` group per `onset_hop` for same-staff simultaneous notes (issue #30's schema), each note's `Note.style.color`/`Chord`-member color set via `note_hex_color()` (the same fixed-lightness fifths-hue mapping `tab`'s own `_tab_note_rgb()` uses, so a score reads the same color live and exported), staff assignment via the existing `staff_map.staff_row()` (middle C and above → treble), and a guessed key signature via `guess_key_signature()` (Krumhansl-Schmuckler correlation against `result.chroma_histogram`, `None`/no-signature below `config.KEY_GUESS_CONFIDENCE_THRESHOLD` — same "blank rather than a wrong guess" posture `chord_templates.match()` already uses). No tuplet detection (issue #62 deferred it) — every duration snaps to `duration_class_for_beats()`'s existing plain/dotted power-of-two set. Each part's note *offsets* (not durations) are quantized to the nearest 32nd-note grid before writing — real (non-quantized) onset times otherwise produce a rest `music21` can't express in MusicXML, reproduced and fixed during issue #65's real (non-synthetic) `--write-score` integration test. Wired into `virtualnote transcribe --write-score [PATH]`, `None` by default (no score written, module not even imported) mirroring `pygame`'s only-imported-inside-`run_gui` convention. `QUARTER_LENGTHS` (duration_class → music21 quarterLength), `note_hex_color()`, and `pitch_for()` are public (promoted from private names for issue #98) so `score_editor_state.py` can reuse them rather than duplicating — see that module's entry and docs/DECISIONS.md. |
**Multi-track projects (map #123, #131):** `write_project(result, path)` writes a `convert.ConversionResult` as one multi-part MusicXML — one part per `<score-part>` by unique `<part-name>` (deduplicated, since #128 measured that is the only part identity surviving a round trip), a versioned JSON manifest in the *score-level* `<miscellaneous>` via `md.setCustom()`, tempo/time/key on the first part (a `MetronomeMark` on the `Score` is silently discarded), and chord spans as MusicXML `<harmony>` on the melody part. `read_project_manifest()` reads it back — note `getCustom()` returns a **tuple of `Text`**, not a string. Onsets go through `_beat_positions()` (linear interpolation against the real beat grid, extrapolating rather than clamping at both ends so a pickup or tail is not piled onto one offset) then `snap_to_grid()` at `BEAT_SUBDIVISIONS` = **12**, the smallest grid holding both binary and ternary subdivision — without it music21 raises *"Cannot convert inexpressible durations to MusicXML"* on the rest it would need between two unquantized onsets. Durations snap through `duration_class_for_beats(allow_tuplets=True)`. Two measured format facts shape this: **music21 does not export `editorial` data at all**, so per-note confidence lives in the manifest as `[beat, midi, confidence]` triples rather than on the notes (a pinning test fails if a future music21 starts exporting it); and **a `ChordSymbol` positioned past the last note is silently dropped**, since measures are only created as far as existing content — so `_pad_to()` extends each part with a trailing rest, which matters because a lead sheet routinely ends on a chord held past the final melody note. An unparseable chord figure is skipped, never fatal. | | `score_editor_state.py` | (issue #98, score editor data layer) The second module permitted to import `music21`, alongside `score_writer.py` — `EditorNote`/`EditorColumn`/`EditorScore` dataclasses are a plain, simple mutable intermediate structure (per #86), keeping music21 confined to this module's own `load_score()`/`save_score()`; no music21 object escapes either function. `new_blank_score()` — `time_signature=(4,4)`, `key_fifths=0`, `tempo_bpm=90.0`, one starting empty (Rest) column, so the cursor always has somewhere to land. `save_score(score, path)` mirrors `score_writer.write_score()`'s two-staff grand-staff / `<chord/>`-grouping / per-note-color structure (reusing its now-public `QUARTER_LENGTHS`/`note_hex_color()`/`pitch_for()`), but walks `score.columns`' own fixed sequence rather than a sparse `onset_hop` map — a Rest column is written as an explicit `music21.note.Rest` on *both* staves (never skipped) so the two parts' offsets stay in lockstep column-for-column, which `load_score()` relies on to merge them back into one flat list keyed by shared offset.
